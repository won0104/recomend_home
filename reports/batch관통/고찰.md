# Spring Batch 관통 프로젝트 고찰

## 1. Batch 구조의 장점과 한계

이번 프로젝트는 Spring Batch의 Tasklet 기반 Step 구조로 구현했다. 전체 흐름은 `estateMarketCollectStep -> estateMarketSaveStep -> estateMarketAiStep -> estateMarketPdfStep` 순서로 구성했다.

이 구조의 가장 큰 장점은 작업 단위가 명확하다는 점이다. 데이터 수집, DB 저장, AI 요약, PDF 생성이 각각 독립된 Step으로 나뉘어 있어 로그를 확인할 때 어느 단계에서 문제가 발생했는지 파악하기 쉽다. 실제 구현 중에도 외부 API 호출 실패, DB 저장 오류, PDF 생성 오류가 각각 다른 Step에서 발생했기 때문에 원인을 빠르게 분리할 수 있었다.

또한 Scheduler와 결합하기 좋았다. 사용자가 직접 요청하지 않아도 애플리케이션 시작 시 또는 지정된 cron 주기에 배치 Job을 실행할 수 있어, 계속 변경되는 부동산 실거래 데이터를 자동으로 갱신하는 구조를 만들 수 있었다.

하지만 한계도 있었다. 현재 구현은 Chunk 기반의 `ItemReader -> ItemProcessor -> ItemWriter` 구조가 아니라 Tasklet 방식이기 때문에, 대용량 데이터를 아주 세밀하게 나누어 처리하거나 실패 지점부터 재시작하는 기능은 상대적으로 약하다. 예를 들어 전국 모든 지역과 여러 개월 데이터를 한 번에 처리할 경우, 특정 지역 또는 특정 페이지에서 실패했을 때 그 지점만 정교하게 재처리하려면 추가 설계가 필요하다.

또한 현재는 테스트 목적상 `lawd-codes=11110`, `max-pages=2`, `max-items=200`처럼 수집 범위를 제한했다. 운영 환경에서는 전국 지역코드, 거래월, 페이지 번호를 반복해야 하므로 API 호출량과 처리 시간이 크게 늘어날 수 있다.

## 2. 데이터 품질이 AI 결과에 미친 영향

AI 요약 결과의 품질은 수집 데이터의 품질에 직접적인 영향을 받았다. 이번 프로젝트에서는 외부 API 응답에서 아파트명, 법정동, 지번, 거래금액, 전용면적, 층, 건축년도, 거래일처럼 요약에 필요한 필드만 추출했다. 불필요한 XML 필드를 제거하고 거래금액을 숫자로 변환했기 때문에 AI가 평균 거래금액, 최고 거래금액, 최저 거래금액 같은 통계를 기반으로 요약을 생성할 수 있었다.

반대로 데이터가 부족하거나 제한적이면 AI 요약도 제한적으로 나왔다. 예를 들어 특정 지역인 종로구와 최근 1개월 데이터만 수집한 경우, AI는 해당 지역의 거래 흐름만 설명할 수 있고 전국 부동산 시장 전체를 대표하는 분석은 할 수 없다. 따라서 AI 결과를 해석할 때는 "수집 범위가 어디까지인지"를 함께 봐야 한다.

데이터 중복도 AI 결과에 영향을 줄 수 있다. 같은 거래가 중복 저장되면 거래량과 평균값이 왜곡되고, AI는 이를 실제 시장 흐름으로 오해할 수 있다. 이를 줄이기 위해 `housedeals` 저장 시 아파트 식별값, 거래일, 거래금액, 면적, 층을 기준으로 중복 삽입을 방지했다.

또한 AI 응답은 Markdown 형식으로 생성되는 경우가 많았다. 처음에는 `#`, `**` 같은 Markdown 문법이 PDF에 그대로 표시되는 문제가 있었다. 이를 해결하기 위해 AI 응답을 HTML로 변환한 뒤 PDF를 생성하도록 처리했다. 즉, AI 결과 자체뿐 아니라 그 결과를 문서로 표현하기 위한 후처리 품질도 최종 산출물 품질에 영향을 주었다.

## 3. 운영 관점에서 개선할 수 있는 부분

현재 구현은 테스트 목적에 맞게 특정 지역(`11110`)과 최근 거래월, 최대 수집 건수를 제한하여 실행한다. 따라서 현재 상태가 실행할 때마다 전국 모든 데이터를 가져오는 방식은 아니다. 다만 운영 환경에서 `lawd-codes=ALL`, `max-pages=0`, `max-items=0`처럼 전체 수집 설정을 적용하면 API 호출량이 많아지고 실행 시간이 길어질 수 있다. 따라서 초기 1회만 전체 데이터를 적재하고, 이후에는 최근 1~2개월 데이터만 주기적으로 갱신하는 방식이 더 현실적이다.

전국 데이터를 다룰 경우에는 지역코드를 한 번에 모두 처리하기보다 지역 그룹을 나누어 순환 갱신하는 방식이 필요하다. 예를 들어 월요일은 서울/경기, 화요일은 충청/강원, 수요일은 전라/경상처럼 나누면 API 호출 부담을 줄이고 실패 범위도 작게 관리할 수 있다.

현재 배치는 Tasklet 방식으로 구현되어 있어 구조가 단순하다는 장점이 있지만, 데이터량이 커지면 Chunk 기반 구조로 확장하는 것이 좋다. `ItemReader`, `ItemProcessor`, `ItemWriter`를 분리하면 대용량 처리, commit 단위 제어, 실패 재시작, skip/retry 정책을 더 정교하게 적용할 수 있다.

모니터링 기능도 추가할 필요가 있다. 현재는 로그와 DB 쿼리로 배치 성공 여부를 확인하지만, 운영에서는 최근 배치 실행 상태, 수집 건수, AI 처리 상태, PDF 생성 경로를 조회하는 관리자 API 또는 화면이 있으면 더 편리하다. 실패 시에는 관리자에게 알림을 보내거나 실패한 Job만 재실행하는 기능도 필요하다.

마지막으로 API Key 관리도 중요하다. 실제 구현 과정에서 API Key가 `application.properties`에 직접 들어가면 Git에 함께 올라갈 위험이 있었다. 이를 방지하기 위해 실제 키는 `application-secret.properties` 또는 환경변수로 분리하고, 해당 파일은 `.gitignore`에 등록하는 방식으로 관리해야 한다.

## 4. 결론

Spring Batch를 적용하면서 기존의 단순 조회 서비스에 자동 데이터 갱신 흐름을 추가할 수 있었다. 외부 API에서 데이터를 수집하고, 필요한 형태로 가공하여 DB에 저장한 뒤, AI 요약과 PDF 생성까지 하나의 Job 흐름으로 연결했다.

이번 구현은 테스트 범위에서는 요구사항을 충족하지만, 운영 수준으로 확장하려면 수집 범위 분할, Chunk 기반 처리가 추가로 필요하다고 판단했다.
