# SSAFY HOME - JSP to Vue SPA 전환 고찰

## 1. 전환 전 구조: JSP 기반 MVC

기존 구조는 Spring MVC 컨트롤러가 JSP view name을 반환하고, 서버가 HTML을 렌더링해서 브라우저에 내려주는 방식이었다. 화면과 서버 렌더링이 강하게 결합되어 있었고, 로그인, 게시판, 공지사항, 주택 정보 같은 기능도 각 JSP 화면에서 직접 처리했다.

### 장점

- 구조가 단순하다.
- 서버가 화면까지 책임지므로 초기 구현 속도가 빠르다.
- HTML 렌더링 결과가 바로 나오기 때문에 별도 프론트 빌드 과정이 필요 없다.
- 세션 기반 로그인과 화면 권한 처리가 자연스럽게 이어진다.
- 작은 규모의 프로젝트에서는 진입 장벽이 낮다.

### 단점

- 화면 로직과 서버 로직이 한 코드베이스에 섞이기 쉽다.
- JSP 수정이 늘어날수록 유지보수가 어려워진다.
- 목록, 폼, 모달 같은 UI를 재사용하기가 불편하다.
- 페이지 단위로 새로고침이 발생하므로 SPA처럼 끊김 없는 경험을 만들기 어렵다.
- 화면 디자인과 기능 확장이 커질수록 JSP 컨트롤러와 view 경로가 복잡해진다.

## 2. 전환 후 구조: Vue SPA + Spring REST API

현재 구조는 화면은 Vue가 담당하고, 백엔드는 JSON REST API만 제공하는 방식이다. 로그인은 Spring Security 세션으로 유지하고, Vue는 Axios로 `/api/**`를 호출해 데이터를 받아 렌더링한다.

### 장점

- 화면과 서버 책임이 분리되어 구조가 명확하다.
- 같은 API를 웹 화면뿐 아니라 다른 클라이언트에서도 재사용할 수 있다.
- `views`와 `components`로 나눠 UI를 재사용하기 쉽다.
- 페이지 전환이 부드럽고, 목록/상세/수정 화면의 사용자 경험을 개선할 수 있다.
- 공통 레이아웃, 모달, 지도, 목록 같은 요소를 독립적으로 관리할 수 있다.
- 백엔드에서는 JSON 응답만 다루므로 API 테스트와 디버깅이 편하다.

### 단점

- 프론트와 백엔드를 따로 실행하고 관리해야 해서 초기 설정이 복잡하다.
- CORS, 세션 쿠키, `withCredentials` 같은 설정을 맞춰야 한다.
- 로그인과 권한 확인을 JSP 태그로 처리하던 방식보다 명시적으로 설계해야 한다.
- 프론트 라우팅, API 호출, 상태 관리까지 함께 고려해야 해서 코드 양이 늘어난다.
- 화면을 완전히 SPA로 옮기는 과정에서 기존 JSP 자산을 재구성하는 비용이 있다.

## 3. Security 처리 고찰

이번 전환에서 보안은 Spring Security의 내장 `formLogin()` 방식이 아니라, REST API 방식의 `POST /api/auth/login`으로 처리했다. 둘 다 Spring Security를 사용하지만, 화면을 누가 렌더링하느냐와 응답 형태가 다르다.

### REST API 로그인 방식

Vue에서 아이디와 비밀번호를 JSON으로 보내면, 백엔드가 `AuthenticationManager`로 인증하고 성공 시 `SecurityContext`를 세션에 저장한다. 브라우저는 `JSESSIONID` 쿠키로 로그인 상태를 유지한다.

#### 장점

- 프론트와 백엔드가 분리된 SPA 구조에 잘 맞는다.
- 로그인 성공/실패 응답을 JSON으로 통일할 수 있다.
- 모바일 앱이나 다른 클라이언트에서도 같은 인증 API를 재사용할 수 있다.
- 로그인 화면, 에러 메시지, 이동 경로를 프론트에서 자유롭게 제어할 수 있다.

#### 단점

- `withCredentials`, CORS, 세션 쿠키 같은 설정을 직접 맞춰야 한다.
- Spring Security의 기본 로그인 흐름보다 구현 코드가 많다.
- 성공/실패/권한 없음 응답을 직접 설계해야 하므로 초기 작업량이 늘어난다.

### Spring Security 내장 로그인 방식

`formLogin()`을 사용하면 Spring Security가 로그인 처리와 리다이렉트를 많이 대신해준다. JSP 같은 서버 렌더링 환경에서는 자연스럽고 빠르게 쓸 수 있다.

#### 장점

- 설정이 단순하다.
- 로그인 성공/실패/세션 관리의 기본 흐름을 Spring Security가 제공한다.
- JSP 기반 화면과 바로 연결하기 쉽다.
- 빠르게 인증 기능을 붙이기에 좋다.

#### 단점

- 성공/실패 후 리다이렉트 중심이라 SPA와 잘 맞지 않는다.
- JSON API 응답 형태로 쓰려면 결국 커스터마이징이 필요하다.
- 화면을 Vue가 담당할 때는 로그인 UX를 프론트에서 세밀하게 제어하기 어렵다.

### 판단

이번 프로젝트는 화면을 Vue SPA로 분리하는 것이 목표였기 때문에, `formLogin()`보다 REST API 로그인 방식이 더 적합했다. 인증 자체는 Spring Security가 계속 담당하지만, 요청과 응답을 API 형태로 바꿔서 프론트가 직접 로그인 흐름을 제어하도록 만드는 것이 구조적으로 더 맞았다.

## 4. 전환하면서 느낀 점

이번 전환에서 가장 중요했던 부분은 "화면을 어디서 렌더링할 것인가"를 명확히 나누는 일이었다. JSP 구조에서는 컨트롤러가 화면과 데이터 둘 다 다뤘지만, Vue SPA 구조에서는 백엔드가 데이터만 제공하고 화면은 프론트가 책임진다.

그 결과 기능별 책임은 더 선명해졌지만, 세션 인증, CORS, API prefix, 컴포넌트 분리 같은 새로운 고려사항이 생겼다. 즉, 구현 난이도는 올라갔지만 구조적 확장성은 훨씬 좋아졌다.

## 5. 결론

JSP 구조는 빠르게 만들기 좋고 단순하지만, 화면 확장과 재사용성 측면에서 한계가 있다. Vue SPA + REST API 구조는 초기 설정이 더 복잡하지만, 장기적으로는 화면 재사용성, 유지보수성, 확장성에서 더 유리하다.

이번 프로젝트에서는 기존 화면 구성과 디자인을 유지하면서도 구조를 분리해야 했기 때문에, JSP의 장점인 빠른 구현성과 Vue의 장점인 재사용성과 분리 구조를 함께 가져가는 방향이 가장 적절했다.
